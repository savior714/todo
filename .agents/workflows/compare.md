## 0. 목적·범위

- **목적**: `docs/specs/`의 **문서 1개(또는 논리적으로 묶인 소수)**를 SSOT로 삼아, **최근 시장에서 타 브랜드·관행**이 어떻게 구현·운영하는지 조사하고, **freeEMR 명세의 수정·보완**으로 이어지게 한다.
- **범위**: 임상 안전·인증 준수·연동·UX·운영 중 본 스펙이 다루는 영역만. 스펙에 없는 임의 확장은 **별도 스펙/플랜**으로 분리한다.
- **산출물**: (1) 비교·갭 분석 기록, (2) 갱신된 스펙 본문 또는 명시적 “변경 없음” 근거, (3) 필요 시 `PROJECT_RULES.md §8`·`docs/knowledge/` 보강.

## 1. Fatal Rules (절대 준수)

- **Docs-First**: 코드·UI 변경이 필요해 보여도 **먼저 `docs/specs/`를 갱신**하고, 구조적 결정은 **`PROJECT_RULES.md §8`**에 대안·채택 이유를 남긴다.
- **근거 고정**: 타사·시장 주장은 **출처(URL·문서명·확인일)** 없이 스펙 본문에 반영하지 않는다. 불확실하면 “가설”로 분리한다.
- **비교 대상 투명성**: “타 브랜드”는 **실명(제품/회사)** 또는 **익명화된 역할**(예: “국내 대형 병원급 EMR A”) 중 하나로 표기하고, 혼동을 막는다.
- **MEMORY Anti-Drift**: 장문 비교표는 **`docs/plans/` 또는 `docs/knowledge/`**에 두고, `AGENTS.md` §2.1.1 참조 — `.agents/memory/MEMORY.md`에는 **링크 1줄**만 추가한다.

## 2. 사전 준비

1. **대상 스펙 선정**  
   - 인덱스: `docs/specs/README.md`, `docs/specs/SPECS_CONSISTENCY_INDEX.md`  
   - 한 세션에 **1개 스펙(또는 동일 주제의 짝 파일 2개 이내)** 권장.
2. **스펙 내부 SSOT 파악**  
   - 헤더의 `Last Verified`, `문서 경계(SSOT)`, 인증 지표·FHIR·UI 등 **교차 참조 링크**를 먼저 읽는다.
3. **로컬 지식 조회**
   - `docs/knowledge/`에 동일 주제 아카이브가 있으면 **웹 검색 전에** 활용한다 (`AGENTS.md` Knowledge Fallback Step 0).
   - **중복 검색 방지**: 이미 `docs/knowledge/`에 아카이브된 정보는 재검색하지 않음.

## 3. 실행 프로토콜 (스펙 1건당)

### Step A — 스펙에서 “비교 단위” 추출

다음을 스펙에서 목록화한다(없으면 본 단계에서 보완 항목으로 표시).

| 추출 항목 | 설명 |
|:---|:---|
| **기능·시나리오** | 사용자/시스템 행위, 예외 흐름 |
| **비기능** | 성능, 가용성, 보안, 감사, 개인정보 |
| **연동·데이터** | 표준(FHIR 등), 메시지, 코드체계 |
| **인증·규제 링크** | A/B/C 지표, 법·고시와의 대응 문장 |
| **용어 체계** | 시장/타사 사용 용어와 freeEMR 표준 용어의 차이 |

### Step B — 시장·타사 조사 (증거 수집)

- **검색·자료 유형(예시)**
  - 국내: 제조사·솔루션 공개 자료, 학회·협회 자료, 보도(보조), **의료정보화 사업·표준 가이드**
  - 해외: 주요 벤더 제품 문서, HL7/FHIR 구현 가이드, 규제·안전 가이드(역할이 맞을 때만)
- **기간 기준**: 조사 시점 기준 **최근 2~3년**을 우선하고, 그 이전 자료는 "역사적 맥락"으로 구분한다.
- **기록 필드(필수)**
  - 출처, 확인일, 스펙 추출 항목과의 **매핑(어떤 행에 대응하는지)**
  - **한계**: 공개 자료만으로 검증 불가한 내용은 "미검증"으로 표시.
- **SearXNG MCP 검색 도구 사용**
  - **`CallMcpTool(server="user-searxng", toolName="searxng_search", arguments={"query":"South Korea EMR 2nd cycle KCD-9 diagnosis code implementation"})`**: 웹 검색 (제목/URL/요약)
  - **페이지 본문 확인은 `WebFetch` 또는 프로젝트에서 활성화된 URL-read MCP 도구를 `CallMcpTool`로 호출**한다.
  - **구체적인 쿼리 사용**: "EMR certification KCD-9 2026"보다 "South Korea EMR 2nd cycle KCD-9 diagnosis code implementation"이 더 정확
  - **토큰 최적화 전략**: 검색 결과에서 가장 신뢰도 높은 **TOP 1~2개 URL**만 본문 확인 수행
  - **결과 검증**: 검색 결과의 신뢰도를 평가하고, 공식 문서/공식 채널을 우선 참조
  - **중복 검색 방지**: 프로젝트 내 `docs/knowledge/`에 이미 자산화된 정보는 재검색하지 않음

### Step C — 비교 매트릭스 (스펙별 1장)

아래 형식을 권장한다(파일 위치는 Step E 참고).

| 비교 축 | freeEMR 스펙(현재) | 타사/관행 A | 타사/관행 B | 근거(링크·일자) | 비고(법·인증·안전) | 용어 매핑 |
|:---|:---|:---|:---|:---|:---|:---|
| … | … | … | … | … | … | … |

**비교 축 예시**: 워크플로우 단계, 알림·차단 정책, 감사 로그 필드, 연동 프로토콜, 오프라인/장애 시 동작, 관리자 설정 범위.

### Step D — 갭 분석 및 조치 등급

| 등급 | 정의 | 스펙 반영 |
|:---|:---|:---|
| **P0** | 인증·법규·환자안전과 직접 충돌 또는 공백 | 스펙에 **필수 요구사항**으로 명시, AC 추가 |
| **P1** | 국내 의료기관 기대 수준과 큰 괴리(운영 리스크) | 스펙에 **권고·설정 가능**으로 구조화 |
| **P2** | 경쟁사 패리티·UX 개선 | 스펙에 **선택·향후** 또는 별도 UI 스펙으로 분리 |
| **Hold** | 근거 부족·제품 전략 미정 | 스펙에 **열린 이슈**로만 기록, `docs/plans/`에 후속 조사 태스크 |

### Step E — 기록 위치 (중복 방지)

- **소규모 갭(수 단락)**: 대상 스펙 하위에 `## 시장·타사 벤치마크(요약)` 섹션 추가. 표는 짧게 유지.
- **대규모 조사**: `docs/plans/YYYYMMDD_{스펙파일 stem}_market_compare.md`에 전체 매트릭스·출처 목록을 두고, 스펙에는 **요약 + 플랜 링크**만 둔다.
- **재사용 가능한 팩트**: `docs/knowledge/{topic}.md`에 아카이브 (`AGENTS.md` Step 5).

### Step F — 스펙 본문 수정·보완

- 변경된 요구사항은 **검증 가능한 문장**(Given/When/Then 또는 체크리스트)으로 적는다.
- **교차 스펙 영향**이 있으면 `docs/specs/SPECS_CONSISTENCY_INDEX.md` 또는 해당 SSOT 문서에 링크를 추가한다.
- 스펙 헤더의 **`Last Verified`**를 갱신한다.
- **내부 정합성 검토**: 수정 사항이 다른 스펙(`docs/specs/SPECS_CONSISTENCY_INDEX.md`)에 영향을 주는지 확인하고, 필요 시 링크를 갱신한다.
- **문서 검증 (필수)**: 문서 수정 완료 후 `python scripts/verify_korean_text.py --dir docs`를 실행하여 한글 인코딩 및 오염 여부를 확인한다.
- **웹 검색 결과 반영 시 주의사항**:
  - **출처 명시**: MCP URL 읽기 도구(`CallMcpTool`)로 가져온 내용은 **정확한 URL + 확인일**을 함께 기록
  - **요약 금지**: 웹 내용을 요약하지 말고, **핵심 문장/표/코드 블록**을 직접 인용
  - **신뢰도 평가**: 공식 문서/공식 채널을 우선 참조, 블로그/포럼은 "비공식"으로 표시

### Step G — 설계 판단이 스펙을 넘어설 때

- 아키텍처·보안·데이터 모델 등 **구조적 선택**이 수반되면 `PROJECT_RULES.md §8`에 **대안·채택 이유·증적**을 기록하고 스펙에서는 링크만 유지한다.

### Step H — 구현 연계 플랜 도출 (자동화된 Handoff)

- `/compare` 분석이 끝나면 에이전트는 향후 후속 작업을 위해 **하단에 2가지 분기로 나누어진 [설계 이관용 프롬프트 (Plan Trigger)]** 마크다운 블록을 반드시 제시한다.
- **분기 1 (Implementation Plan)**: P0, P1 같이 실제 시스템(코드/UI/DB) 수정이 즉각 필요한 항목들을 `/plan`으로 넘기기 위한 프롬프트.
- **분기 2 (Research Plan)**: Hold이거나 추가 시장 조사/R&D가 필요한 항목을 `/plan`으로 넘기기 위한 프롬프트.
- **출력 예시**:
  ```text
  ⚙️ **다음 세션/단계로의 이관 프롬프트 (복사하여 사용하세요)**

  [분기 1: 구현 설계용]
  > /plan 실행. 대상소스: `docs/plans/YYYYMMDD_{건명}_compare.md`. 도출된 P0, P1 항목을 중심으로 스펙 구현을 위한 백엔드/프론트엔드 작업 단위(Task) 분해 시작.

  [분기 2: 후속 리서치용]
  > /plan 실행. 대상소스: `docs/plans/YYYYMMDD_{건명}_compare.md`. Hold 항목 등 추가 리서치가 필요한 부분에 대한 조사 계획, 평가 태스크 배정.
  ```
