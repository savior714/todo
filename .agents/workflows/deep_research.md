## 0. 목적·범위
- **목적**: 내부 검색 능력을 초과하는 복잡한 규제 해석이나 거시적 기술 트렌드 파악을 위해 외부 딥 리서치 모델 전용 프롬프트를 생성하고, 결과를 프로젝트 SSOT에 반영함.
- **범위**: 의료법/약사법 개정, EMR 인증 기준 변화, 신규 프레임워크/스택의 장기적 안정성 검토 등.
- **산출물**: (1) 최적화된 리서치 프롬프트, (2) 리서치 결과 아카이브, (3) 갱신된 스펙 및 설계 결정 로그.

## 1. Fatal Rules (절대 준수)
- **법적 해석 분리**: 리서치 결과 중 확정되지 않은 법적/규제 해석은 스펙 본문이 아닌 `## 검토 필요 (Pending Review)` 또는 `부록` 섹션에 격리 저장함.
- **프롬프트 자산화**: 효과적인 질문은 `docs/knowledge/research_prompts/`에 버전 관리하여 영구 보존함.
- **개인정보 비식별화**: 외부 모델에 질문 시 프로젝트의 민감 정보(개인키, 환자 데이터, 보안 토큰)는 반드시 제거하고 추상화된 컨텍스트만 제공함.

## 2. 실행 프로토콜

### Step A — 리서치 필요성 진단
- 다음 상황 발생 시 `/deep-research` 워크플로우를 트리거함.
  - 마일스톤 시작 전 규제 영향도 파악이 필요할 때.
  - 특정 기술 도입의 3년 이상 장기적 로드맵이 불확실할 때.
  - 프로젝트 내 `docs/knowledge`만으로 해결되지 않는 복합적 에러/성능 병목 발생 시.

### Step B — 컨텍스트 추출 및 프롬프트 생성
- **에이전트 역할**: 현재 프로젝트의 관련 스펙(`docs/specs/`) 및 플랜(`docs/plans/`)을 읽어 리서치 대상 모델(예: OpenAI o1)이 이해하기 쉬운 고밀도 컨텍스트를 생성함.
- **결과물**: `docs/knowledge/research_prompts/YYYYMMDD_{subject}_V{n}.md` 형식으로 프롬프트 생성.

### Step C — 외부 리서치 수행 (사용자 협업)
- 사용자는 생성된 프롬프트를 복사하여 외부 딥 리서치 도구에 입력함.
- 생성된 결과물(Markdown, PDF 등)을 `docs/knowledge/research_results/YYYYMMDD_{subject}.md` 위치에 저장함.

### Step D — 결과 분석 및 SSOT 반영
- **GAP 분석**: 리서치 결과와 현재 프로젝트 설계 간의 차이점 식별.
- **반영**:
  - 기술적 결정 -> `PROJECT_RULES.md` §8 갱신.
  - 기능적 요구사항 -> `docs/specs/` 보완 (법적 해석은 별도 섹션 유의).
  - 구현 태스크 -> `/plan` 워크플로우로 이관.

### Step E — 프롬프트 최적화 (Loop)
- 리서치 결과의 퀄리티를 평가하고, 프롬프트의 페르소나나 질문 구조를 개선하여 `docs/knowledge/research_prompts/` 내 지식을 업데이트함.

## 3. 품질 체크리스트
- [ ] 생성된 프롬프트에 프로젝트 민감 정보가 포함되지 않았는가?
- [ ] 법적 해석 사항이 별도의 '검토 필요' 섹션으로 격리되었는가?
- [ ] 리서치 결과 원본이 `docs/knowledge/research_results/`에 아카이브 되었는가?
- [ ] 갱신된 스펙의 `Last Verified` 날짜가 업데이트 되었는가?

## 4. 이관 프롬프트 (Plan Trigger)
리서치 결과가 기술 부채 해결이나 신규 기능 구현으로 이어질 경우:
> /plan 실행. 대상소스: `docs/knowledge/research_results/YYYYMMDD_{subject}.md`. 딥 리서치 결과 중 확정된 기술적 구현 사항을 중심으로 Task 분해 시작.
